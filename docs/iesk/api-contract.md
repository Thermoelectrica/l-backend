# API-контракт: IESK-осмотры и их синхронизация (для l-mobile)

Версия контракта: 1.0 (2026-11-19, задача #72). Статус: согласован, backend в реализации.

Документ самодостаточен: в нём всё, что нужно mobile для работы с IESK-станциями и IESK-осмотрами. Обоснования и детали реализации — в [backend-plan.md](backend-plan.md), [sync-flow.md](sync-flow.md), [mobile-implementation.md](mobile-implementation.md).

---

## 1. Суть

- Некоторые станции заведены как **IESK-станции**. Это видно по полю `external_plant_type: "iesk"` в ответах `/plant`.
- Для них появляется **дополнительный** тип осмотра — IESK-осмотр (`/iesk-inspection`). Это упрощённый осмотр без шагов: одна запись с чек-листом, комментарием, статусом и фото.
- Обычные осмотры (`/inspection`) продолжают работать на **всех** станциях, включая IESK. Сервер ничего не блокирует.
- **Какой тип осмотра предлагать пользователю, решает mobile** по `external_plant_type`. При PUT сервер тип станции не проверяет и записывает осмотр как есть.
- Фото работают так же, как в обычном осмотре: `PUT /image` + загрузка в S3 по presigned URL, а в осмотре хранится список ссылок `image_links`.
- Синхронизация устроена так же, как у остальных агрегатов: `server_modified_at` служит и версией, и курсором, плюс оптимистичная блокировка (409), `force`, логическое удаление.

## 2. Общие правила

| Правило | Значение |
|---------|----------|
| Базовый URL, авторизация | как для остальных ручек: `Authorization: Bearer <jwt>` или `X-Auth-Token` |
| Формат дат | ISO-8601 с часовым поясом, сервер отдаёт UTC, например `2026-11-19T08:31:12.345678Z` |
| Сравнение `server_modified_at` | с точностью **до миллисекунд** |
| Идентификаторы | UUID генерирует клиент; `inspector_id` — целое |
| Неизвестные поля в ответах | игнорировать (сервер может добавлять поля) |
| Неизвестные поля в запросах | сервер игнорирует |
| Курсор `modified_since` | строго `>`: возвращаются записи с `server_modified_at > modified_since`. Не передан → все записи (сервер подставит `1790-01-01`) |
| Логическое удаление | физического удаления нет: `is_deleted: true` приходит в pull как «надгробие» |
| Сжатие | ответы ≥ 1000 байт приходят в gzip (`Content-Encoding: gzip`), OkHttp распаковывает сам |

## 3. Признак станции: изменения в `/plant`

### 3.1 Новое поле

| Поле | Тип | Где | Значения |
|------|-----|-----|----------|
| `external_plant_type` | `string \| null` | `GET /plant/all` (каждый `items[]`), `GET /plant/by_id/{id}`, ответы `PUT /plant`, `POST /plant/by_id/{id}/claim`, `POST /plant/by_id/{id}/release` | `"iesk"` — IESK-станция; `null` — обычная. Ключ присутствует всегда. Незнакомое значение трактовать как `null` (на будущее). |

Остальные поля `Plant` и `PlantListItem` не меняются.

### 3.2 Правила
- Поле **только для чтения.** В `PUT /plant` его можно не передавать, а переданное значение сервер игнорирует. Старые клиенты без этого поля продолжают работать.
- **Источник истины на устройстве — ответ `GET /plant/all`** (мобильное приложение уже запрашивает его целиком, `modified_since` не передаётся). Сохранять значение в `plant_metadata` при каждом обновлении списка, **без** сравнения `server_modified_at`.
- Станции размечаются на сервере вручную, и `server_modified_at` станции при этом **может не измениться**. Поэтому опираться на `GET /plant/by_id` и локальную копию `plant` для определения типа нельзя.
- Признак могут снять. Тогда UI перестаёт предлагать новые IESK-осмотры, а уже созданные продолжают синхронизироваться как обычно.

## 4. Модель `IeskInspection`

Одна и та же модель служит ответом GET и телом PUT.

| Поле | Тип | Обяз. в PUT | По умолчанию | Описание |
|------|-----|:---:|---|---|
| `id` | UUID | да | — | генерирует клиент |
| `equipment_id` | UUID | да | — | оборудование, на котором проводится осмотр. По нему сервер определяет станцию |
| `inspector_id` | int | да | — | инспектор (id из токена или `TokenStorage`) |
| `started_at` | datetime | да | — | начало осмотра |
| `completed_at` | datetime \| null | нет | `null` | время завершения |
| `status` | `"PLANNED"` \| `"IN_PROGRESS"` \| `"COMPLETED"` | нет | `"PLANNED"` | тот же enum, что у `Inspection.status` |
| `oil_level` | int \| null | нет | `null` | чек-лист: уровень масла |
| `bugs` | int \| null | нет | `null` | чек-лист: насекомые |
| `dimensions` | int \| null | нет | `null` | чек-лист: габариты (в постановке было `dimentions`, в API — **`dimensions`**) |
| `locks` | int \| null | нет | `null` | чек-лист: замки |
| `stickers` | int \| null | нет | `null` | чек-лист: ТИН (наклейки) |
| `comment` | string \| null | нет | `null` | свободный текст |
| `is_deleted` | bool | нет | `false` | логическое удаление |
| `server_modified_at` | datetime | **да** | — | версия записи. **Для нового осмотра** передавать любое значение, например `started_at` (как сейчас делается для `Inspection`): у новых записей сервер метку игнорирует. **Для существующего** — значение из последнего ответа сервера |
| `image_links` | `IeskImageLink[]` | нет | `[]` | фото осмотра |

Поля чек-листа — целые числа без ограничений диапазона. Связи `status` и `completed_at` сервер не проверяет, как и у `Inspection`.

`IeskImageLink`:

| Поле | Тип | Описание |
|------|-----|----------|
| `image_id` | UUID | id изображения, созданного через `PUT /image` |
| `is_deleted` | bool | в ответах `true` у отвязанных фото («надгробие»). В PUT передавать `false` (или не передавать) |

Пример:
```json
{
  "id": "0b6f9a52-7f0e-4d6b-a2a5-6c5b1e7d9f01",
  "equipment_id": "9a1c4d2e-1111-4c3b-8d1e-5a6b7c8d9e0f",
  "inspector_id": 7,
  "started_at": "2026-11-19T08:30:00Z",
  "completed_at": "2026-11-19T08:42:00Z",
  "status": "COMPLETED",
  "oil_level": 1,
  "bugs": 0,
  "dimensions": 2,
  "locks": 1,
  "stickers": 3,
  "comment": "Течь масла не обнаружена",
  "is_deleted": false,
  "server_modified_at": "2026-11-19T08:43:12.345Z",
  "image_links": [
    {"image_id": "c3d2e1f0-2222-4a1b-9c8d-7e6f5a4b3c2d", "is_deleted": false},
    {"image_id": "d4e3f2a1-3333-4b2c-8d9e-0f1a2b3c4d5e", "is_deleted": true}
  ]

```

`IeskInspectionListItem` (только в `/all`): `id`, `equipment_id`, `inspector_id`, `started_at`, `completed_at`, `status`, `is_deleted`, `server_modified_at`.

## 5. Эндпоинты `/iesk-inspection`

### 5.1 `GET /iesk-inspection/by_plant_id/{plant_id}` — основной для синхронизации
| | |
|---|---|
| Query | `modified_since` (datetime, необязательный) |
| Ответ 200 | **голый массив** `IeskInspection[]` (полные агрегаты с `image_links`, включая надгробия), отсортирован по `server_modified_at` по возрастанию |
| Права | доступ к станции |
| Ошибки | 403 нет доступа к станции |

Для станции без IESK-осмотров вернётся `[]`. Вызывать ручку можно для любой станции.

### 5.2 `GET /iesk-inspection/by_id/{id}`
| | |
|---|---|
| Ответ 200 | `IeskInspection` |
| Ошибки | 404 не найден; 403 нет доступа к станции |

Используется при разрешении конфликтов: перечитать серверную версию (стратегия THEIRS, перезапрос записей в конфликте).

### 5.3 `PUT /iesk-inspection` — создание и изменение
| | |
|---|---|
| Query | `force` (bool, по умолчанию `false`) |
| Тело | `IeskInspection` целиком |
| Ответ 200 | сохранённый `IeskInspection` с **новым** `server_modified_at` и актуальными `image_links` (включая надгробия) |
| Права | уровень `INSPECT` и выше + доступ к станции оборудования. **Захват станции (claim) не нужен.** Тип станции не проверяется |

Поведение:
- Записи с таким `id` нет → создаётся (переданный `server_modified_at` игнорируется).
- Запись есть, `force=false` → `server_modified_at` из тела должен совпасть с серверным (до мс), иначе 409.
- Запись есть, `force=true` → перезаписывается без проверки версии.
- `image_links` синхронизируются **как у обычного осмотра**: каждая присланная ссылка активна, а ссылки, которых нет в теле, сервер помечает `is_deleted=true` (при любом `force`). Чтобы отвязать фото, достаточно не включать его в список.
- Удаление осмотра: PUT с `is_deleted: true`.

### 5.4 `GET /iesk-inspection/all`
| | |
|---|---|
| Query | `modified_since` |
| Ответ 200 | `{"items": IeskInspectionListItem[]}` — только по доступным станциям |

Для синхронизации не нужен, добавлен для единообразия API.

## 6. Ошибки

| Код | Когда | Тело |
|-----|-------|------|
| 400 | несуществующее `equipment_id` в PUT; прочие ошибки данных | `{"detail": "<текст>"}` |
| 400 | нарушение ограничений БД (например, несуществующий `inspector_id`) | `{"type": "foreign_key_violation", "message": "<текст>"}` (без `detail`) |
| 403 | нет доступа к станции или недостаточный уровень доступа | `{"detail": "<текст>"}` |
| 404 | `by_id` не найден | `{"detail": "IESK inspection not found"}` |
| 409 | версия устарела (`force=false`) | `{"detail": ConflictError}`, см. ниже |
| 422 | невалидное тело (тип поля, неизвестный `status`, нет обязательного поля) | `{"type": "request_validation_error", "message": "<текст>"}` |
| 401 | токен недействителен | как у остальных ручек |

`ConflictError` (внутри `detail`):
```json
{
  "detail": {
    "type": "conflict",
    "message": "IeskInspection was modified by another client",
    "server_modified_at": "2026-11-19T08:43:12.345Z",
    "client_modified_at": "2026-11-19T08:31:00.000Z",
    "conflicts": [
      {"field": "server_modified_at", "message": "Timestamp mismatch",
       "server_value": "2026-11-19T08:43:12.345000+00:00", "client_value": "2026-11-19T08:31:00+00:00"}
    ],
    "extra_child_ids": []
  }
}
```
Серверной версии записи в теле 409 **нет**: её нужно получить через `GET /by_id/{id}`.

Сопоставление с `toPushResult` на mobile: 409 → `Conflict`, 400 → `Error` (ошибка конкретной записи, синхронизация продолжается), 401/403/5xx/сеть → как сейчас.

## 7. Фото (без изменений API)

1. Сделали фото → локально создать `Image` с `plant_id` станции осмотра. Связь создаётся одновременно с ним: `image_id` добавляется в `image_links` осмотра, осмотр становится dirty.
2. При синхронизации: `PUT /image` (как сейчас), в ответе приходит presigned URL для загрузки.
3. Файл загружается в S3 существующим механизмом (`ImageSyncWorker`), сервер получает callback и ставит `upload_status=UPLOADED`.
4. `PUT /iesk-inspection` с `image_links`. Порядок относительно загрузки файла не важен: внешних ключей между агрегатами нет.
5. Скачивание: `GET /image/by_plant_id/{plant_id}` / `GET /image/by_id/{id}` → `presigned_url`, как сейчас.

Дополнительных проверок нет (в том числе «фото той же станции»), логика та же, что у `inspection_image_link`.

## 8. Алгоритм синхронизации IESK-осмотров

Отдельная стадия в `BidirectionalPlantSyncCoordinator.syncPlant`, через общий `BidirSyncAlgorithm`. Ставится **после** Equipment (2), Image (3) и Inspection (4) и **до** Defect (5).

**Когда выполнять**: если `plant_metadata.external_plant_type == "iesk"` **или** на устройстве есть IESK-осмотры этой станции. Допустимо выполнять всегда: для обычной станции сервер вернёт `[]`.

**Pull** (сначала при SKIP/THEIRS, после push при OURS):
1. `modified_since = max(server_modified_at)` локальных IESK-осмотров станции; при полной синхронизации не передавать.
2. `GET /iesk-inspection/by_plant_id/{plant_id}?modified_since=…`.
3. Обработать записи по возрастанию `server_modified_at`. Для каждой записи `R`, где `L` — локальная запись с тем же id:
   - `L` нет → вставить `R`, clean;
   - метки `L` и `R` равны (до мс) → пропустить;
   - `L` не dirty → перезаписать `R`, clean;
   - `L` dirty → по стратегии: SKIP — если бизнес-данные равны, clean, иначе конфликт; THEIRS — перезаписать; OURS — оставить локальную.
   - Сохраняя `R` локально, **отбрасывать ссылки с `is_deleted: true`**.
4. Записи в конфликте при инкрементальной синхронизации перечитать через `GET /by_id/{id}`.

**Push**:
1. Взять dirty IESK-осмотры станции (при SKIP пропустить те, что в конфликте).
2. `PUT /iesk-inspection?force=<strategy == OURS>` с текущим набором ссылок.
3. 200 → сохранить ответ как clean (новый `server_modified_at`, ссылки без надгробий). 409 → по стратегии (SKIP: пометить конфликт; THEIRS: `GET /by_id` и перезаписать; OURS: конфликт «forced update rejected»). 400 → ошибка записи, остаётся dirty.

**Сравнение бизнес-данных** (`isBusinessDataEqualTo`, ложные конфликты после потерянного ответа): все поля из §4, кроме `server_modified_at`, плюс **множество** `image_id` активных ссылок без учёта порядка.

**Локальные изменения**: создание → `server_modified_at = null`, `is_dirty = true`; любое изменение полей или фото → `is_dirty = true`; `server_modified_at` клиент сам никогда не меняет.

## 9. Чего этот контракт не меняет

- `/inspection`, `/equipment`, `/defect`, `/image`, claim/release — без изменений.
- Периодичность осмотров и критичность дефектов: IESK-осмотры **не учитываются**.
- Журнал `/log`: отдельного `entity_type` для IESK пока нет. При необходимости писать `INSPECTION` с `data.kind = "iesk"`.
